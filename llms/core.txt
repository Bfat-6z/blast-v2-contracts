# Blast contracts: Shared core integrator reference

> Everything an integrator needs to understand and call Blast's shared money vocabulary on Sui: basis points and exact apportionment, recipients and vested payouts, LP-fee splits, the protocol-fee ledger with partner cuts, the treasury, Merkle proofs, and the sealed migration hand-off between a sale and its venue. Sui mainnet only.

This file is self-contained: give it to an AI agent and ask it anything about Shared core. It also covers the packages its calls depend on: `blast_partners`, `blast_admin`. Other products are in [llms-full.txt](https://github.com/interest-protocol/blast-v2-contracts/blob/main/llms-full.txt), which joins every product in one file.

How it is organized:

1. **Packages and deployment status**: each package, whether it is live on Sui mainnet, and its IDs.
2. **Guides**: how each product works end to end, starting with the calling conventions every product shares. Each product guide opens with its deployment status. Use them for behavior, flows, economics, and pitfalls.
3. **API reference**: generated from the Move source. Every public function and type with its doc comment, every event, every abort code, and the package constants. Use it for exact signatures and field layouts.

When the guides and the reference disagree, the reference is right: it is generated from the source on every change. When this file does not say a behavior exists, treat it as unsupported. Source for every module is linked from the reference ([repository](https://github.com/interest-protocol/blast-v2-contracts)).

Conventions: amounts are atomic units of the coin named; rates are basis points (BPS) out of 10,000; timestamps are Unix milliseconds from Sui's shared `Clock` at `0x6`, while durations and delays are elapsed milliseconds. Types are written as Move: `module::Type` names a type in another module of the same package, `package::module::Type` one in another Blast package, and well-known Sui framework types appear bare.

## Calling Blast contracts

Every Blast product is a set of Sui Move packages called from programmable
transaction blocks (PTBs). This section covers what every product shares. Each
product guide below assumes it.

### Products and packages

| Product | What users do | Packages |
| --- | --- | --- |
| Presale | commit Quote to a capped or overflow sale, claim tokens or refunds, earn LP fees and holder rewards after migration | `blast_presale`; one-off partner migrators such as `blast_aftermath_dao_presale` |
| Launchpad | launch a coin on a bonding curve, trade it, graduate it into a DEX pool | `blast_fun` (curve, lifecycle, fees), a generated coin package per launch, `blast_fun_migrators` (venue start, migration, LP vault, LP fees, holder rewards) |
| Partner codes | earn a share of Blast's fee on the flow an app brings | `blast_partners` |
| Boosts | hold a leveraged long or short coin backed by Aftermath perpetuals | `blast_boosts_core`, `blast_boosts_products`, `blast_boosts_aftermath` |
| blastSUI | stake SUI with one validator through funSUI and blastSUI | `blast_sui` |
| Administration | Blast's operators manage roles, fees, and upgrades | `blast_admin` |

Each package and what it depends on:

```text
blast_fun_migrators          -> blast_fun, blast_admin, Cetus, Bluefin
blast_fun                    -> blast_partners, blast_admin
blast_partners               -> blast_admin
blast_presale                -> blast_admin, blast_partners, blast_fun_vesting, Cetus, Bluefin, Aftermath
blast_aftermath_dao_presale  -> blast_presale, Aftermath AMM
blast_boosts_aftermath       -> blast_boosts_core, blast_partners, blast_admin, Aftermath perpetuals
blast_boosts_core            -> blast_admin
blast_sui                    -> blast_admin, Sui system
blast_admin                  -> Sui framework only
```

The launchpad imports no DEX. A migrator package depends on the launchpad and
composes with it inside one PTB. Presale uses typed roles from the shared
`blast_admin` ACL and holds migrated liquidity in its own `presale_vault::Vault`.
Use the presale guide for presale calls.

`blast_fun_vesting` (used by `blast_presale`) lives in this repository at
`sui/vesting` and is immutable on mainnet. The standalone
OTC package lives at `sui/otc`. See the [utility integration guide](https://github.com/interest-protocol/blast-v2-contracts/blob/main/docs/utilities.md).

### Time values

Timestamp parameters ending in `_at_ms` are points in time measured in Unix
milliseconds. Duration parameters ending in `_duration_ms` are lengths of time;
`_delay_ms` parameters are offsets from the documented anchor. For example,
`commitment_starts_at_ms + commitment_duration_ms` is the commitment window's
end timestamp. Stored fields and event payloads retain their published names;
read their documented meaning rather than assuming every `_ms` value is a
timestamp. Framework calls such as `Clock::timestamp_ms` retain their native
names.

### Building a call

- **Target.** A call is `moveCall` with target
  `<package-id>::<module>::<function>`. Use the package ID (`published-at`) from
  the deployment table.
- **Type arguments.** Pass fully qualified type strings. A Blast type is named by
  the package that first defined it (`original-id`), even after an upgrade.
- **`TxContext`.** A trailing `ctx: &TxContext` or `&mut TxContext` parameter is
  supplied by Sui. Leave it out of the arguments.
- **Shared objects.** Pass a shared object by ID. A `&` parameter takes it
  read-only, `&mut` or by value takes it mutably; mutable access orders the
  transaction through consensus with every other writer of that object.
- **System objects.** `Clock` is `0x6` (always `&Clock`), the Sui system state is
  `0x5`, and the Coin Registry is `0xc`.
- **Coins in.** A function that takes `Coin<T>` by value consumes it whole. Split
  the exact amount first (`SplitCoins`; for SUI, split from the gas coin) and
  merge several coins first when needed (`MergeCoins`).
- **Values out.** Most Blast functions return coins and objects instead of
  transferring them. Every returned value without the `drop` ability must be used
  before the PTB ends: transfer it (`TransferObjects`), pass it to a later call,
  or merge it. A value with no abilities at all (a "hot potato", such as a
  launch initializer or a migration handoff) can only be consumed by the specific
  later call that accepts it, so the whole sequence must sit in one PTB.
- **Basis points.** Each package that takes rates defines its own validated
  `Bps` type in its `bps` module. Build one inside the PTB with that package's
  constructor, for example `blast_presale::bps::new` or `blast_fun::bps::new`,
  which aborts above 10,000. A `blast_fun` `Bps` is a different type from a
  `blast_presale` `Bps`.
- **Options.** Pass `Option<T>` arguments with `0x1::option::some` or
  `0x1::option::none` calls, or as pure BCS-encoded options.

### Reading state

- **Getters** are public functions that take `&` objects and return values. Run
  them through a dev-inspect or simulated transaction to read without signing
  or paying.
- **Object fields** can be read directly from a full node and decoded with BCS.
  The API reference prints every struct with its fields in declaration order,
  which is the BCS order. Fields are readable on chain even though Move code
  outside the module cannot access them.
- **Per-user records** (commitments, claims) usually live in dynamic fields
  keyed by a small key struct the reference lists; read them with the
  dynamic-field RPC calls.
- **Events** reconstruct history; contract state and completed events are the
  source of truth, and any off-chain preview is an estimate.

### Versions and upgrades

Upgrade rules depend on the package lineage.

| Posture | Packages | What callers do |
| --- | --- | --- |
| Immutable | `blast_admin`, `blast_partners`, `blast_boosts_core`, `blast_aftermath_dao_presale` | Nothing: the code never changes. |
| Dependency-only | Historical presale publications | These older lineages can relink venue packages and do not use an operational version object. |
| Version-gated | `blast_presale`, `blast_fun`, `blast_fun_migrators`, `blast_sui`, `blast_boosts_aftermath` | Mutating calls take the package's shared version object. After an upgrade advances it, calls through an older package ID abort with a version mismatch, so always call the current ID. |
| Additive | `blast_boosts_products` | Upgrades only add product tags; it holds no state. |

### Events

- Query events by their Move type, named with the `original-id`.
- `blast_fun`, `blast_sui`, and `blast_boosts_aftermath` wrap every payload in
  the `Event<T>` envelope of their own `blast_events` module (for example
  `blast_fun::blast_events::Event`), so the event type is
  `<original-id>::blast_events::Event<<original-id>::<module>::<Payload>>`.
  Every other package emits payload structs directly.
- Sui orders events by checkpoint, transaction, and event index within the
  transaction; payloads carry no sequence numbers of their own.
- The reference lists every event struct under its module with its fields.

### Errors

A failed call returns a Move abort naming the module and function that aborted
and a `u64` code. Blast uses two styles:

- **Named errors** (`#[error]` constants): `blast_partners`,
  `blast_fun_migrators`, and `blast_aftermath_dao_presale`. Sui's RPC and SDKs
  decode these into the constant's name and message; the reference lists each
  module's constants with their messages.
- **Numeric codes**: `blast_fun`, `blast_presale`, `blast_sui`, `blast_boosts_core`,
  `blast_boosts_aftermath`, and `blast_admin` abort with small integers. Look the
  number up in that package's abort-code table in the reference.

The abort names the module where it happened, which may be a package called
underneath the one you called: a migrator call can abort inside `blast_fun` or
`blast_admin`, and an abort in a Cetus, Bluefin, or Aftermath module comes from
the venue. Simulate a transaction before signing to see its abort without
spending gas.

### Network

Blast deploys only to Sui mainnet. There is no testnet deployment, faucet, or
test address. Try a transaction with a mainnet simulation (dev-inspect or dry
run) before signing it.

## Shared core

> **Deployment status:** `blast_core` is not yet published on mainnet; its interface may change before publication.

### What it is

Package `blast_core` holds the money building blocks every Blast launch product shares, each
defined once: a basis-points unit and its exact apportionment, recipients and their vested or
outright payouts, the LP-fee split, the ledger that holds Blast's fees and pays the partner's cut,
the one treasury address, Merkle proofs, and the sealed values that carry a sale's liquidity to its
venue and prove a sale's ownership to its vault. It holds no user funds of its own. Products and
vaults embed its values and call it; integrators read its events and build PTBs that pass its
values between product and venue calls.

### Units and payouts

- `blast_core::bps::Bps` is a rate from 0 to 10,000 basis points; `blast_core::bps::new` aborts
  above 10,000. `blast_core::bps::apply_up` and `blast_core::bps::apply_down` round in the named
  direction.
- `blast_core::bps::apportion` splits an amount over rates that sum to exactly 10,000 by largest
  remainder: every part takes its floor, an optional named part takes its ceiling, and the
  leftover units go one each to the largest remaining remainders, earlier parts first. The parts
  always sum to the amount.
- `recipient::Recipient` is a nonzero address with a share and optional `recipient::VestingTerms`.
  `recipient::pay_or_vest` pays a recipient's amount as a coin, or locks it in an irrevocable,
  shared `blast_fun_linear_vesting::Vesting` schedule that starts at the payout and returns its ID.
  A zero amount sends nothing.

### Fee splits

`fee_split::FeeSplit` is a list of up to 16 routes summing to 10,000. Each route has a positive
share and a `fee_split::Destination`: an address, the vault's owner, auto-LP, holder rewards, or
burn. No address and no special kind appears twice. `fee_split::apportion` divides one collection
across the routes in order.

### Protocol fees, partners, and the treasury

`protocol_fees::Ledger` holds Blast's Meme, Quote, and SUI fees for one launch, presale, or vault.
`protocol_fees::take_share` moves Blast's rounded-up share of a fee into it. A ledger is bound at
creation to the partner its sale named, or to none. `protocol_fees::pay` pays everything to the
treasury and aborts when a partner is bound; `protocol_fees::pay_with_partner` first pays that
partner its cut of each asset through `blast_partners::blast_partners::pay`, then the treasury the
rest. Both emit `protocol_fees::ProtocolFeesPaid`. Products expose these payouts as calls anyone
may make.

`blast_treasury::Treasury` is a shared singleton holding the address Blast's fees go to. A Blast
admin with `blast_domain::TreasuryAdmin` schedules a new address with
`blast_treasury::schedule_destination`; anyone applies it with `blast_treasury::apply_destination`
once its notice has passed (48 hours from publication); a Blast admin with
`blast_domain::CancelAdmin` cancels it with `blast_treasury::cancel_destination`. Read the current
address with `blast_treasury::destination`.

### Migration hand-off and owner proof

- Before a sale's supply is minted, its venue prepares the coin and returns a
  `migration::VenueBinding` sealed by the venue's witness, naming the venue and its
  `migration::PoolTier`. The product's creation call consumes it with `migration::unbind` and
  stores the venue.
- At migration the product returns a `migration::Migration` sealed by its own witness, holding the
  pool's Meme and Quote and the new vault's `migration::VaultTerms`: the sale, the product, the
  fee split, Blast's LP-fee shares, the partner, and whether residuals go to Blast or the owner.
  Only the stored venue can consume it, with `migration::redeem`; any other venue aborts.
- `owner_proof::OwnerProof` is a product's sealed statement that the caller holds the sale's
  creator authority. A vault consumes it with `owner_proof::verify`, which aborts unless it names
  the vault's product and sale.

None of these values can be dropped, copied, or stored, so the PTB that creates one must consume it.

### Merkle proofs

`blast_core::merkle::verify` checks a positional Blake2b-256 proof of a leaf digest at an index. Internal nodes
hash as `blake2b256(0x01 || left || right)`; an odd node at any level is its own sibling. Each
consumer hashes its own leaves under its own domain prefix. Malformed roots, digests, or siblings,
an empty tree, an index outside it, or a proof of the wrong depth return false instead of aborting.

### Roles

`blast_domain` declares Blast's product roles for the shared ACL: `TreasuryAdmin`, `FeeAdmin`,
`ListingAdmin`, `AdapterAdmin`, `RewardsAdmin`, `BuybackAdmin`, `CreatorAdmin`,
`ClaimSignerAdmin`, and `CancelAdmin`. Only Blast admins hold them.

### Errors

Every abort is a small integer from the package's numeric registry; the reference lists each code.
The abort names the module that raised it.

## API reference: `blast_core` (Shared core)

Not yet published on mainnet. Its interface may change before publication.

Events: payload structs are emitted directly, each under its own type.

Abort codes: this package aborts with the numeric codes below from whichever module detects the failure; the abort location names that module.

| Code | Constant | Meaning |
| --- | --- | --- |
| 0 | `EInvalidBps` | A basis-points rate must be at most 10,000. |
| 1 | `EInvalidApportionment` | Apportioned rates must sum to 10,000 and name a rounded-up part inside them. |
| 2 | `EInvalidVestingTerms` | Vesting needs positive steps whose total and cliff fit the technical bound. |
| 3 | `EInvalidRecipient` | A recipient must be a nonzero address. |
| 4 | `EInvalidRecipients` | Recipients must be within capacity, positive, distinct, and vested only where allowed. |
| 5 | `EInvalidRoute` | A route needs a positive share and a nonzero address. |
| 6 | `EInvalidFeeSplit` | A fee split needs at most 16 distinct routes summing to 10,000. |
| 7 | `EInvalidTreasury` | The treasury must be a nonzero address. |
| 8 | `EInvalidPair` | The Meme and Quote types must differ. |
| 9 | `EPartnerMismatch` | Blast's fees pay with exactly the partner the sale named, or with none. |
| 10 | `EWrongVenue` | Only the venue the sale stored can redeem its migration. |
| 11 | `EWrongOwner` | The owner proof must name the vault's product and sale. |

### `blast_core::blast_domain`

Blast's product administration roles in the shared Blast ACL, one set for the launchpad, the presale, the vault, and the venues (ADR 0137). Package-infrastructure roles (upgrade, pause, unpause) are generic over each package's marker in `blast_admin`.  A role is a type. An `AdminCap` holding `Role` signs in to `AdminWitness<Role>`, and a function's witness parameter names the one role it accepts, so no role authorizes another's actions.

### `blast_core::constants`

Package-wide core constants exposed as zero-cost macros.

Source: https://github.com/interest-protocol/blast-v2-contracts/blob/main/sui/core/sources/constants.move

#### Constants

- `basis_points_denominator: u64 = 10_000`: Denominator for rates expressed in basis points.
- `max_routes: u64 = 16`: Maximum routes in one fee split; every collection pays them in the same transaction.
- `max_vesting_duration_ms: u64 = 1 << 63`: A technical bound on a vesting schedule's duration: from any clock below 2^63 ms, about 292 million years, the schedule's end still fits in u64, so payout cannot overflow creating it.
- `digest_length: u64 = 32`: Byte length of a Blake2b-256 digest: Merkle roots, leaves, and proof siblings.
- `initial_treasury_delay_ms: u64 = 48 * 60 * 60 * 1_000`: Notice every treasury change waits from publication: the genesis destination is compiled, so no setup needs a zero notice.

### `blast_core::migration`

The sealed contract between a sale and the venue that migrates it.  Before supply leaves the sale's `TreasuryCap`, a venue prepares the coin and returns a `VenueBinding` sealed by its witness; the product admits and stores the binding's venue. At migration the product opens a `Migration` sealed by its own witness, carrying the pool's balances and the new vault's terms, and only the stored venue's witness can redeem it. Neither value can be dropped, copied, or stored, so a transaction completes the migration whole or aborts.

Source: https://github.com/interest-protocol/blast-v2-contracts/blob/main/sui/core/sources/migration.move

#### Types

```move
/// The pool tier a venue reserved for the coin: Cetus and Bluefin take a tick spacing and fee
/// rate; Aftermath takes no tick spacing and its DAO fee as the rate.
public struct PoolTier has copy, drop, store {
    tick_spacing: u32,
    fee_rate: u64,
}

/// What happens to the migration residuals the pool does not take.
public enum ResidualPolicy has copy, drop, store {
    /// Paid to Blast through the vault's protocol ledger.
    Protocol,
    /// Held in the vault for the sale's owner to claim.
    Owner,
}

/// Everything a new vault snapshots from the sale that opened it.
public struct VaultTerms has copy, drop, store {
    /// The launch or presale the vault belongs to; owner proofs name it.
    origin: ID,
    /// The original type of the product witness that opened the hand-off.
    product: TypeName,
    fee_split: fee_split::FeeSplit,
    /// Blast's share of each LP-fee collection, per asset.
    protocol_meme_bps: bps::Bps,
    protocol_quote_bps: bps::Bps,
    partner_id: Option<ID>,
    residuals: ResidualPolicy,
}

/// A venue's sealed preparation of one coin, consumed by the product that admits it.
public struct VenueBinding {
    venue: TypeName,
    tier: PoolTier,
}

/// One sale's pool balances and vault terms, redeemable only by `venue`.
public struct Migration<phantom Meme, phantom Quote> {
    meme: Balance<Meme>,
    quote: Balance<Quote>,
    venue: TypeName,
    terms: VaultTerms,
}
```

### `blast_partners::blast_partners`

Blast partner codes, shared by every Blast product.  A partner is one deal: it is paid a share of the fee Blast charges on every trade that names it, in the same transaction. A company holds one `PartnerCap` for all its deals, each a separate partner with its own share. Blast's partner administrator registers partners under a cap, proposes each one's share, and can propose moving a partner to another cap; the cap's holder sets where each of its partners is paid. Initial terms apply at registration. A later share or cap applies only when someone applies it, no sooner than `PARTNER_CHANGE_DELAY_MS` after it was proposed. That notice is fixed: this module never changes it, and the package is published immutable. The recipient the cap holder sets applies at once.  Products call `pay` with Blast's own fee on a trade. `pay` emits `PartnerPaid` for what the partner received; the product records the trade and the amount in its own event. Share and cap lifecycle events come from `blast_admin::delayed`, keyed by `ShareKey` and `CapKey` and owned by the partner.

Source: https://github.com/interest-protocol/blast-v2-contracts/blob/main/sui/partners/sources/blast_partners.move

### `blast_admin::delayed`

Settings that change only after their applied notice, and the deadline rules every delayed type shares.  A timelock in the Compound/OpenZeppelin sense: schedule, wait the applied notice, then apply; cancellable until applied. Settings live here; one-shot actions in `delayed_action`, allowlists in `delayed_set` and keyed values in `delayed_map`.  Every value carries an owner-defined key `K` and the ID of the object that stores it. Constructors take that object's `&UID`, which only the code creating or holding the object has, so no package can attribute a value or its events to another's object. Owners use a struct without a public constructor as `K`, so only their module can pack it. Each delayed module emits every lifecycle fact of its type, generic in `K` and carrying `owner`; owners emit only their own side effects.  Every change, a shorter notice included, waits the notice applied when it was scheduled. A notice can start at zero, so a schedule and its apply in one transaction then act as a setter; there is no other mutation path. No notice exceeds `max_delay_ms`, so a notice can always be changed again. Readers need no Clock.

Source: https://github.com/interest-protocol/blast-v2-contracts/blob/main/sui/admin/sources/delayed/delayed.move
